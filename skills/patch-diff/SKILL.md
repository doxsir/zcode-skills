# Skill: патч-диф анализ закрытых уязвимостей

Используй, когда нужно понять, как работала уже пропатченная уязвимость, а
публичного writeup'а нет (или он слабый). Триггер: «разбери по патч-дифу»,
«что там починили в Patch Tuesday», «как работала эта CVE».

## Порядок работы

1. **Достань две версии.** Для Windows — из каталога обновлений Microsoft или
   Winbindex; для open source — коммит-fix в репозитории проекта.
2. **Продиффай.** BinDiff/Diaphora для бинарников, `git diff` для open source.
   Ищи не «все изменения», а функции, где появились новые сравнения размеров,
   длины и границ — это почти всегда и есть фикс.
3. **Найди место бага по фиксу.** Новая проверка `if (len > MAX)` в функции X =
   раньше X принимала длину без проверки. Восстанови, какой вход делал len
   больше MAX.
4. **Определи класс.** Переполнение, integer overflow, UAF, link following,
   race — класс подсказывает примитив эксплойта.
5. **Оцени достижимость.** Кто может дотянуться до функции? Локально/по сети?
   Нужна ли аутентификация? Это разница между «критично» и «интересно».

## Что писать в разбор

- Root cause своими словами (не пересказ адвизори)
- Скрин/цитата дифа: было → стало
- «Как бы я это искал без патча» — план фаззинга или ревью
- Ссылки: адвизори, диф, похожие баги того же автора/класса

## Инструменты

- BinDiff / Diaphora — бинарь-vs-бинарь
- `git log -p` / GitHub compare — опенсорс
- winbindb.com — скачивание конкретных версий системных dll Windows

## Честность

Если по дифу не восстановил root cause — так и пиши: «фикс добавляет валидацию X,
вероятная причина — Y, требует проверки». Не выдумывай уверенность.
