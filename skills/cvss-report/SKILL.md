# Skill: CVSS 3.1 оценка багбаунти-репорта

Используй этот скилл, когда нужно поставить CVSS 3.1 оценку найденной уязвимости
или проверить оценку из репорта. Триггер: пользователь просит «оцени по CVSS»,
«какой скор у этой уязвимости», «проверь вектор».

## Что делает

1. Разбирает метрики уязвимости по чеклисту ниже.
2. Считает base score (скриптом `cvss31.py` или вручную по формулам).
3. Объясняет выбор каждой метрики одной фразой — это главная ценность, не число.

## Чеклист метрик

- **AV** — как доставляем эксплойт? N: по сети, A: соседняя подсистема (LAN, VPN, общая память), L: локальный доступ, P: физический.
- **AC** — нужны ли условия вне контроля атакующего? L: сработает всегда, H: нужны редкие условия (win race, специфичный конфиг).
- **PR** — какие права нужны ДО эксплойта? Смотри внимательно: если уязвимость в multi-tenant системе и затрагивает ДРУГИХ пользователей — Scope Changed.
- **UI** — должен ли кто-то кликнуть/открыть?
- **S** — может ли ударить по ресурсам ЗА границей security scope? (other users, other tenants, service itself) → Changed.
- **C/I/A** — что именно теряем: конфиденциальность, целостность, доступность. H = тотал или критичный ресурс, L = частично.

## Считаем

```bash
python3 cvss31.py AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H
```

Вывод: вектор, base score, severity band, разбор метрик.

## Частые ошибки оценки (проверяй на них)

- Забыли Scope Changed для multi-tenant → занижение.
- PR:L стоит когда атакующий уже имеет аккаунт → это правильно, не завышай до PR:N.
- UI:R забыли в stored XSS, где нужен просмотр жертвой.
- C/I/A:H когда дамп памяти даёт только фрагменты → это L.
- Требование аутентификации забывают в PR — «админ может сделать это легально»
  не означает PR:H; оценивай от позиции обычного пользователя с минимальными правами.

## Спецификация

Формулы и веса: FIRST CVSS 3.1 specification (first.org/cvss/v3.1/specification).
Не выдумывай веса — скрипт содержит таблицы из спеки.
