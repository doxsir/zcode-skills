# Skill: triage багбаунти-репортов

Используй, когда нужно оценить входящий репорт уязвимости: валиден ли, дубликат ли,
какой приоритет. Триггер: «протриажь репорт», «валиден ли этот репорт», «дубликат?».

## Порядок триажа

1. **Reproduce по шагам из репорта.** Не воспроизводится → вернись к автору один раз
   с конкретным вопросом, не «unable to reproduce», а «на шаге 3 я вижу X, уточни».
2. **Проверь scope.** Уязвимый домен/эндпоинт в программе? Нет → out of scope,
   вежливо и с указанием, какая программа этим занимается.
3. **Найди первоисточник.** Это уже известная CVE / чужой writeup / известный dup
   внутри программы? Дубликаты — 30% входящего потока.
4. **Оцени реальный импакт**, а не заявленный. Автор пишет «RCE»? Проверь: часто это
   «арбитрary file read» или XSS в админке. Импакт-инфляция — норма жанра.
5. **CVSS 3.1** через скилл `cvss-report` (см. соседнюю папку).
6. **Верdict**: accepted (priority по импакту), needs-info (один конкретный вопрос),
   duplicate (ссылка на оригинал), informative (почему не фиксируется + совет),
   out-of-scope (какая строка policy).

## Красные флаги слабых репортов

- Скриншот без шагов воспроизведения
- Сканер-вывод (burp/nuclei) без понимания, почему это уязвимость
- «Возможен RCE» без единого доказательства исполнения
- Impersonation-риск без описания конкретного вектора
- SQLi по ошибке 500 (может быть что угодно)

## Тон ответов

Уважительный даже к мусорным репортам. Сегодняшний «информативный» — завтра
найдёт что-то настоящее и будет помнить, как с ним обошлись.
